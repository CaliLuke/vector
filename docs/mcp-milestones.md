# Native milestone domain and MCP contract

## Summary

Vector needs a project-owned milestone domain to execute the pinned `milestone` tool and PQL's milestone field. A milestone is not an alias for a module. Each live work item has at most one milestone, and its milestone belongs to the same workspace and project. HTTP, MCP and PQL share the native domain; transport code must not implement a separate store or mutate through an HTTP loopback.

This document defines the entire seven-action milestone contract. Implementing a schema or query alone does not complete any missing action. Teamspace access grants are a separate domain decision and remain required for full PQL parity.

## Evidence and current state

The pinned [handler](https://github.com/makeplane/plane-mcp-server/blob/dc7cfd9f3c305891909e2372f0cc507291353801/plane_mcp/tools/milestone.py) calls SDK 0.3.1 `Milestones`, normalizes the exact empty optional string to omission, and applies additions before removals in `manage_workitems`. Its lists use the toolkit's seven-field envelope. The SDK's milestone record has `id`, required `title`, `target_date`, `external_source`, `external_id`, `created_at` and `updated_at`; association rows have `id`, `issue`, and `milestone`. Unknown SDK fields are allowed, but no undocumented field is required here.

The current [product contract](https://docs.plane.so/projects/milestones) states project ownership, one milestone per item, unique titles within a project, optional target dates, and archive state inherited from the project. Deleting a milestone unlinks items without deleting them. These facts settle domain cardinality; the pinned handler/SDK remain the transport compatibility target. Current upstream role names are not a migration of Vector's existing roles.

At design time Vector had no milestone table, native application operation or HTTP design. Migration 000018 now supplies the canonical schema and revisions, and `internal/issuequery` resolves milestone PQL through its shared `MilestoneReadScopeSQL` permission rule. `internal/milestones` implements the seven shared application operations, including snapshot reads, receipts, revision checks and transactional outbox writes. These operations are not mounted. The item-activity worker now records milestone title/UUID snapshots, admits subscriber notifications and retries email delivery with current recipient scope and preferences. History and notification UI render these snapshots explicitly. Fresh milestone visibility filtering in history/profile/notification readers and HTTP/MCP adapters remain pending. Migration 000019 adds the explicit webhook opt-in, exposed by the existing webhook management API. The webhook worker projects milestone records and preserves the workspace UUID through model expansion, fanout and delivery; focused native-outbox tests cover admission reconciliation, delivery retry, unsubscribe and slug reassignment. `internal/workitems` supplies shared item visibility, transactional item changes and `work_item_effects` admission. `internal/mutationreceipts` supplies optional receipt transactions. `internal/backgroundtasks` owns durable effect delivery. Existing `internal/djangoapi.ProjectMemberReadScopeSQL` is the general fresh project-read boundary; the milestone rule adds archive and guest restrictions. `mcp/design` and generated MCP output remain the catalogue source of truth.

## Goals and boundaries

Support all seven pinned actions, the PQL field, safe project-scoped authorization, durable effects and optional receipt/CAS extensions. Ordinary requests retain the pinned shapes and do not require extensions. No new client-side query implementation, implicit feature activation, unrelated role migration or teamspace grant is introduced. UI layouts, milestone description editing and progress visualizations are not inputs or results of this pinned MCP contract. They must not be advertised as implemented by this domain work.

## Ownership and schema

A new native `internal/milestones` application boundary owns reads, validation, writes, associations and public domain errors. Its proposed HTTP design is isolated under `apps/go-api/milestones/design`; shared authored record/envelope fields live in its `design/types` subpackage, following the existing `invitationsmembership/design/types` pattern. Both the HTTP design and `mcp/design` consume those field definitions. Generated transport output is regenerated from the affected source designs only. `internal/mcpactions` adapts credential-neutral application commands and projects the pinned MCP envelope; it does not perform SQL.

The canonical schema contains `milestones` with UUID identity, workspace/project ownership, nonempty title after trimming leading/trailing ASCII whitespace (space, tab, CR, LF, vertical tab and form feed; maximum 255 Unicode characters), optional calendar target date, nullable external identity strings, creation/update attribution and timestamps, and soft-deletion time. Duplicate live titles use exact case-sensitive equality after trimming, scoped to a project. External identity is metadata, not an alternate upsert key. UUIDs and ownership never change. A milestone has no independent archive timestamp: the project's archive state determines read/write availability.

`milestone_issues` retains a stable UUID per association, milestone/issue/project/workspace IDs, creation/update attribution and timestamps and soft-deletion time. A partial unique index enforces at most one live association per issue. Composite ownership constraints ensure each endpoint belongs to the row's project and workspace; endpoint ownership changes cannot leave a live foreign relationship. A deleted association does not reserve the item. Stored nullable live endpoint keys enforce ownership and target liveness through foreign keys, including under concurrent writes and older snapshots. A historical association retains its item identity without blocking a later item move; live associations must first be removed. Re-adding after unlink creates a new association ID; adding an already-live same association is a no-op. The service additionally validates endpoint deletion/draft/intake/archive eligibility under locks. Read predicates independently enforce ownership and liveness, including when malformed imported data exists.

A milestone revision covers its authored row and its live association set. A separate revision table and database triggers cover every milestone/association writer, including native HTTP and future workers; reads do not advance it. Moving a link advances both affected milestone revisions. Revision rows survive soft deletion, allowing receipt replay and conflict reconciliation without resurrection. Projection is an opaque token bound to the milestone UUID and monotonic counter. It excludes derived item state, names and progress because those are not fields mutated by a milestone command. Item-domain revision coverage must also include milestone relationship changes when core item CAS is introduced; this contract cannot claim that unfinished item-CAS work is complete.

## Authorization and transaction policy

Every read binds the authenticated workspace UUID as well as slug and uses the primary database. It verifies a live actor/workspace and live unarchived project, active workspace membership in a known role, and active correctly-owned project membership in the same read snapshot. For this new domain, project members/admins (15/20) may read; role 5 may read only when `guest_view_all_features` is true. A restricted guest cannot infer milestone existence through lists, detail or PQL. This uses Vector's existing guest distinction rather than importing a new Commenter role. Existing cycle/module permissions do not change.

Writes require active workspace membership and active project membership with role 15/20 in a live unarchived project. A workspace administrator does not gain a new implicit bypass of the selected project's existing membership boundary. Contributor delete is allowed for any milestone, not limited to its creator. These rules apply to HTTP and MCP alike. A selected project that fails scope admission returns the existing project-denial category; an absent, foreign or deleted target within an admitted scope returns not-found. Invalid inputs return validation errors without raw SQL, stored titles or private operand lists.

Use read-only repeatable-read transactions for multi-statement list/count/projection and use the same transaction for authorization. Mutations use the existing `mutationreceipts.Execute` transaction. Revalidate credentials after receipt-key waiting, then authorize and lock live account/workspace/project/membership rows through commit. Read a matching receipt before target lookup/CAS. Destructive replay authorizes the surviving project scope without requiring the deleted milestone. Request conflicts, stale revisions, expiry and indeterminate commits follow `docs/mcp-writes.md`.

Mutations lock project scope before milestone rows; association commands lock involved milestones in ascending UUID order and then items in ascending UUID order. Recheck authorizations and state after waits. No optimistic pre-read authorizes a write. All writers of the new domain follow this order. Database uniqueness remains the last line of defense under concurrent assignment.

## Action matrix

| Action           | Input/defaults                                                 | Shared operation and result                                                                          | Rejection / no-op                                                                                                                                     |
| ---------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| list             | required project; cursor; page size 0/omitted = 1000, max 1000 | live milestones ordered target date ascending, NULL last, UUID tie-breaker; seven-field MCP envelope | invalid cursor/size; hidden project is not an empty page                                                                                              |
| retrieve         | project and milestone UUID                                     | seven SDK fields; all nullable fields explicit null                                                  | foreign/deleted/missing milestone                                                                                                                     |
| create           | project, nonblank title; optional date/external metadata       | create record and return SDK shape                                                                   | duplicate normalized title, invalid date, archived project; no automatic upsert                                                                       |
| update           | project, milestone; optional title/date/external metadata      | patch only supplied nonempty pinned fields; return SDK shape                                         | empty normalized title when explicitly supplied through native HTTP; the exact empty MCP string means omission; unchanged patch is a successful no-op |
| delete           | project, milestone                                             | soft-delete milestone and all live links; ordinary MCP returns empty content                         | already deleted is not-found unless recovered by a valid receipt                                                                                      |
| list_workitems   | project, milestone; same pagination                            | live association records `{id,issue,milestone}` for visible items; same seven-field envelope         | target masking; no full work-item substitution                                                                                                        |
| manage_workitems | project, milestone; normalized add/remove UUID arrays          | atomically apply additions, then removals; ordinary MCP empty content                                | both lists empty; any invalid/unavailable item aborts whole request; duplicate IDs collapse; overlap ends removed                                     |

The application and HTTP layer use the same records. HTTP list responses may carry the existing twelve-field SDK pagination carrier, projected by MCP to the pinned seven-field envelope; field meaning, cursor position, count, order and visibility must agree. Page counts are computed after visibility. Cursor parsing uses `internal/djangoapi.CursorPage` and envelope construction uses `djangoapi.Envelope`. HTTP requires a positive explicit page size (1–1000); an absent size defaults to 1000, and an explicit zero or empty string is a validation error. MCP zero/omitted size and empty cursor are omitted before invoking the shared operation, matching `page_params`; HTTP an absent cursor starts page zero and a present empty cursor is invalid. Negative sizes/pages and overflowing offsets are rejected without running the item query. Both surfaces use the existing three-component cursor syntax and page arithmetic. Association order is association `created_at` ascending, then association UUID ascending, independent of item dates or titles.

Calendar dates use validated `YYYY-MM-DD` in years 0001–9999, never server-local midnight timestamps. Native HTTP may explicitly clear nullable date/external metadata with null; pinned MCP exact empty optional strings remain omission because that is what `opt` and `exclude_none` send. A nonempty whitespace-only title reaches native validation and fails after ASCII trimming. Null title is invalid on both create and patch. External identity strings are preserved byte-for-byte, including whitespace, with a 255-character limit; native HTTP null clears them, but an exact empty string supplied through MCP is omitted. A nonempty whitespace-only date is invalid, not omission. Ordinary outputs contain only the seven SDK milestone fields or three link fields; revision metadata is opt-in. `include_revision` on detail and optional `request_id`/`expected_revision` on existing-resource mutations follow the project's established opt-in extension pattern. Creation supports a receipt but rejects `expected_revision`. When either mutation extension is supplied, the exact result is `{milestone_id,revision,result}`; `result` is the seven-field milestone record for create/update and JSON null for delete/manage. A keyed result additionally contains `request_id,replay_expires_at,replayed`; those keys are absent without a request ID. The same wrapper shape is used on first result and replay. Detail `include_revision=true` adds only `revision` to its otherwise ordinary record. Default empty delete/manage results remain empty. Normalized receipt inputs distinguish omitted versus null, use canonical lowercase UUIDs, deduplicate and sort each add/remove array lexically, and retain the two arrays separately (including overlap). Array permutations are equivalent; different requested arrays that happen to have the same eventual effect are not equivalent. Include normalized `expected_revision` when supplied.

The two list actions share one generated MCP page carrier. Its entry is a typed carrier with common required nullable `id` and optional typed milestone/link fields; application projection emits exactly one permitted shape, never a mixed record. This avoids two indistinguishable empty-page result union branches and the existing nested-union limitation tracked in Loom #1036. The record/link shapes are asserted before transport serialization and by goldens. No field uses an untyped map as a replacement for the contract. Remove the merged-entry carrier when a released nested-union fix supports the exact page-entry union. HTTP uses separate concrete record/link endpoints, sharing authored field definitions. A single page variant, ordinary record and extension wrapper have distinct required outer fields, so an empty `results` array is unambiguous.

## HTTP routes

Under `/api/v1/workspaces/{slug}/projects/{project_id}/milestones/`, GET lists (200), POST creates (201). `/{milestone_id}/` supports GET/PATCH (200) and DELETE (204). `/{milestone_id}/work-items/` supports GET (200 association page), POST and DELETE (204) with JSON body `{"issues":["uuid",...]}` for additions/removals. The SDK's separate requests each invoke the same shared association command with one list empty; MCP invokes that command once with both lists and one receipt/CAS scope. These generated routes use existing HTTP authentication and primary scope binding. They neither redirect through legacy module endpoints nor introduce a second writer. Unsupported verbs fail through generated routing. Mutation extensions produce a 200 JSON wrapper on operations that would otherwise return 204; create retains 201. Native HTTP unknown input fields are rejected by the authored schema.

## Association, archive and PQL behavior

Adding requires live, visible, non-draft, non-archived, non-intake work items in the same project. An item already assigned to another milestone returns a conflict; `manage_workitems` does not silently move it. Removal from this milestone is idempotent for a valid same-project item with no current link, and never removes another milestone's link. For a normalized item ID, let `before` mean a live link to this milestone. Validate every operand first, then compute `after=(before OR added) AND NOT removed`:

| Before | Added | Removed | After / identity                 | Revision and item effects |
| ------ | ----- | ------- | -------------------------------- | ------------------------- |
| no     | yes   | no      | linked with new association UUID | advance; one addition     |
| yes    | any   | no      | same live association UUID       | unchanged; none           |
| yes    | any   | yes     | old association soft-deleted     | advance; one removal      |
| no     | any   | yes     | still unlinked; no transient row | unchanged; none           |
| no     | no    | no      | unlinked                         | unchanged; none           |

Effect/revision behavior follows net state, not transient add-then-remove intermediate state. This is the atomic native command's policy; the pinned handler's final removal-wins result is preserved, without promising its two-request intermediate observations. The whole request is one transaction, even though the pinned client makes separate add/remove HTTP calls. An invalid removal cannot leave successful additions committed. Existing links survive later item archival and are available to appropriately archived item queries; a new attachment cannot be made to an archived item. Soft-deleted and draft items never appear in link reads. Archived projects cannot be read or mutated through these milestone routes; restore the project to access its retained milestones. A milestone PQL relation in an archived project is invisible. Archived items within an unarchived project can still retain a readable milestone relation.

Milestone PQL is a cardinality-one relationship with set-style empty behavior: `=`, `IN`, `!=`, `NOT IN`, `IS NULL` / `IS EMPTY`, and their negations. Empty/unreadable association makes equality false, negative membership true, and empty tests true, matching existing relationship collection semantics. Resolve only live, correctly-owned links and milestones that the actor can read in the item's project, always inside outer item visibility. No target name matching or UUID-existence oracle; missing/foreign/hidden UUIDs are an empty relation. Do not expose a hidden milestone through negative predicates, counts or OR branches. PQL does not create or enable milestone data. Feature presentation toggles, when exposed by project feature APIs, do not delete or unlink retained data; their API/PQL behavior must be pinned before advertising such toggles.

Intake eligibility uses the existing PQL definition: a live, correctly-owned `intake_issues` bridge to a live `intakes` row, regardless of triage state. A state-group label alone does not make an item intake. Apply these rules after project/workspace admission:

| Item state                                      | New attachment | Removal operand    | Association list / PQL relation                                                         |
| ----------------------------------------------- | -------------- | ------------------ | --------------------------------------------------------------------------------------- |
| live, non-draft, non-archived, no intake bridge | allowed        | allowed/idempotent | visible when actor can read item and milestone                                          |
| live archived item in active project            | reject         | allowed/idempotent | retained link visible; outer item route decides whether archived candidates participate |
| live intake item                                | reject         | allowed/idempotent | retained link visible if item is visible; no automatic unlink                           |
| draft or soft-deleted item                      | reject         | masked not-found   | omitted / empty relation                                                                |
| missing or foreign item                         | reject         | masked not-found   | omitted / empty relation                                                                |

Deleting a milestone soft-deletes every live owned association, including hidden draft/deleted-item remnants, without returning their IDs/counts. Item history/notification effects are admitted only for nondeleted, nondraft linked items; all other cleanup is covered by the milestone deletion event. No deletion path changes or deletes work items.

## Durable effects

Every effective milestone create/update writes a `webhook` outbox entry using the existing `plane.bgtasks.webhook_task.model_activity` admission with `model_name="milestone"`. Delete uses the existing direct `plane.bgtasks.webhook_task.webhook_activity` admission with `event="milestone"`, `verb="deleted"` and `event_id` equal to the milestone UUID; it must not attempt to serialize the deleted row through model activity. Both paths carry authenticated actor, workspace slug, origin and stable outbox identity in the existing admission envelope. The emitted event is `milestone`, with action `created`, `updated` or `deleted`; create/update payload is the seven-field record plus owning project/workspace identifiers, and delete payload is `{id}`. Updated events carry the existing per-field old/new activity envelope for only changed fields. New `webhooks.milestone` is false by default and is exposed through the existing `workspace_webhooks/design` and `internal/workspacewebhooks` management boundary under its existing permissions. Fanout must explicitly select active, live hooks in the same workspace with `milestone=true`; it must never fall through to the current unfiltered unknown-event path. Model serialization and ownership validation recognize only the new authored milestone model. Existing hook event flags do not subscribe to milestones implicitly. Association add/remove and delete-induced unlinks produce one item activity/subscriber-notification admission and one item-updated webhook admission per changed item. These must use the current native background workflows and stable outbox identities, extended to recognize the milestone field, not a synchronous publisher or invented task name. A no-op emits nothing; replay emits nothing again. If an effect cannot be serialized or admitted to the outbox, rollback the domain change and receipt. External delivery remains retryable and at-least-once; exactly-once delivery is not claimed. Item activity uses the authored field `milestone`, storing old/new milestone UUIDs and display-title snapshots in the current item-activity envelope, and the associated item webhook event remains `issue` with action `updated` and field `milestone`. Subscriber notifications follow the existing issue-activity workflow. Audit snapshots survive milestone soft deletion and remain scoped to the owning item/workspace. New milestone-field handling must be explicitly routed through the existing activity serializer and notification renderer; merely accepting an arbitrary field string is not proof of delivery.

## Proof obligations

Real PostgreSQL proof covers unique live assignment under concurrency, same-owner constraints, title normalization/collision, add/remove overlap and atomicity, empty versus hidden scope, guest policy, membership revocation after admission/waits, workspace slug reassignment, archived/deleted endpoints, complete pagination/counts and association UUID shape. PQL proof covers positive, negative, empty and NOT/OR predicates with foreign/malformed/deleted links and restricted guests. Native and MCP projections must match the pinned SDK/handler fixture, under PAT and generic OAuth and both protocol revisions. Receipt replay precedes CAS, reauthorization precedes replay, stale versions conflict, every writer advances the correct revision, and rollback suppresses domain/outbox/receipt changes together. Worker retry and subscriber/webhook observations prove durable effect behavior. Required full quality gates and live proxy verification remain completion requirements, not substitutions by unit tests or schema presence.
